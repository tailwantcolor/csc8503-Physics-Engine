# 游戏设计理论基础知识库（叙事 · 玩法循环 · 体验设计）

> 目的：为后续关于「玩法设计方向」的讨论提供共同语言、可追溯的来源和可执行的检查表。
> 范围：故事设计、游戏叙事、玩法循环、体验设计，以及贯穿其上的 AAA 质感与玩法创新。
> 性质：对经典理论与行业实践的**综合整理**，不是任何一本原著的替代品；引用与争论请以原始作品为准。

## 为什么需要这份知识库

游戏设计讨论最常见的失败不是「没有想法」，而是：

1. **各说各话**：有人谈叙事、有人谈数值、有人谈手感，彼此不在同一层抽象上；
2. **只偏一侧**：要么故事很完整但玩家没事可做，要么循环很顺但不知道为什么要玩；
3. **无法判断**：一个提案听起来很酷，却说不清它让玩家多做了什么决定、成本多少、风险在哪；
4. **经验不可复用**：这次讨论的结论下次就丢了，没有沉淀成可检查的标准。

这份知识库把「叙事性」和「玩法性」放在同一张桌子上：先定义体验目标，再同时检查故事线、循环线和品质线。它不提供唯一答案，只提供**判断依据**。

## 三条主线与一条横线

- **叙事线**：故事设计（`01`）+ 游戏叙事（`02`）。关注「为什么做」与「做了什么意味着什么」。
- **玩法线**：玩法循环（`03`）。关注「反复做什么」「做什么决定」「为什么继续」。
- **体验线**：体验设计（`04`）。关注「玩家感觉到什么」「反馈是否可读」「难度是否公平」。
- **品质与创新横线**：`05`。它不独立存在，而是对上面三条线的完成度、一致性和差异化提出要求。

三条线不是三个部门，而是同一个体验的三种视角。任何一条线单独成立，游戏都可能「能玩但不好玩」或「好看但不像游戏」。

## 怎么用

### 5 分钟速查（讨论前）

读 `06-design-discussion-playbook.md` 的「讨论前先对齐的五件事」，并确认本次讨论要回答的是哪一类问题：

- 体验目标不清 → 先谈 `04` 的体验目标与情感词表；
- 不知道玩家反复做什么 → 先谈 `03` 的核心循环一页纸；
- 故事和玩法两张皮 → 先做 `06` 的「叙事—玩法整合审计」；
- 提案很新但心里没底 → 用 `05` 的创新评估表打分；
- 品质没底 → 用 `05` 的分阶段品质门槛表。

### 30 分钟对齐（立项/方向讨论）

1. 用三个形容词写出体验目标（`04`）；
2. 用一句话写出「玩家是谁、在什么情境下、反复做什么、获得什么」（`03`）；
3. 用一句话写出「故事的问题是什么、玩家用什么动作回答它」（`01` + `02`）；
4. 用一句话写出「本作区别于同类的那一个点」（`05` 的创新主张）；
5. 把以上四条写成设计支柱，并各自给出「我们做 / 我们不做」的边界（`06`）。

### 深度讨论（评审/拆解）

- 先用 `05` 的案例拆解法拆一个参考作品：它解决的是什么体验问题？用了什么机制？代价是什么？
- 再用 `06` 的评分表给当前方案打分，分数低的那一项就是下一轮要补的。
- 每次讨论结束必须留下「决策记录」：问题、选项、证据、决定、验证方式、负责人。

## 概念卡格式

本知识库中的概念尽量按同一结构展开，便于引用和争论：

```
概念名（英文）
- 定义：一句话说清它是什么。
- 解决什么问题：它被发明出来是为了处理哪种设计困境。
- 怎么用：在讨论/设计中的具体动作。
- 常见误用：看起来像但它不是的东西。
- 来源：A/B/C 级来源（见下）。
```

## 证据分级

| 级别 | 含义 | 例子 |
| --- | --- | --- |
| A | 经典理论：经过长期讨论的著作、论文、框架 | Schell《The Art of Game Design》、MDA 论文、Jenkins 的叙事架构 |
| B | 行业实践：GDC 演讲、开发者文章、可复核的案例拆解 | 某工作室公开的 postmortem、GDC talk |

讨论时请区分：**A 是依据，B 是参考，C 是假设**。C 级判断可以被推翻，但推翻时要给出证据，而不是换一个 C。

## 十条先记住的结论

1. **先定体验目标，再选机制**：机制是手段，体验是目的。
2. **核心循环必须能在 30 秒内说清**：说不清，通常不是玩家听不懂，而是设计没想清。
3. **叙事问题尽量由玩法动作回答**：玩家做了什么，比玩家看了什么更有说服力。
4. **每个机制都要能回答「它让玩家做什么决定」**：没有决策的机制只是操作。
5. **反馈先于奖励**：玩家先要知道「我做到了」，才谈得上「我得到了」。
6. **难度是一种体验语言**：它表达威胁、节奏和主题，不只是数值曲线。
7. **创新优先「新动词 / 新关系 / 新约束」**，而不是新皮肤、新题材。
8. **AAA 质感 = 完成度 × 一致性 × 可读性**，预算只是实现条件之一。
9. **用垂直切片证明，而不是用文档说服**：能玩的一分钟胜过十页 PPT。
10. **先做减法**：删掉不服务支柱的内容，比再加一个系统更能提升品质。

## 维护约定

- 新增概念必须给来源（A 或 B）；只有 C 级判断时明确标注「经验法则」。
- 概念去重：同一概念只在一个文件里定义，其他文件用链接引用。
- 案例只写「可观察的设计事实 + 可迁移的结论」，不写无法核实的传闻与数字。
- 每季度复核一次链接与案例；失效链接改为「书名/标题 + 作者」，不保留死链。
- 本知识库刻意保持**项目无关**：不写入具体项目的设定、剧情与未公开信息；项目内容放在项目自己的设计文档里。
- 本知识库服务讨论，不替代具体项目的设计文档；项目决策仍以项目文档和评审记录为准。
